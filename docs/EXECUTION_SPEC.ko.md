# 실행 관리자 상세 설계 v0.1

작성일: 2026-10-24. 상태: 검토용 설계안, 미구현.

기존 PLAN.ko.md의 확정 원칙을 구체화한다. 아래의 제안 기본값은 사용자 확정값과 구분한다. GitHub 게시는 별도 확인 후 수행한다.

## 1. 확정 원칙

- Codex 구현, Claude 독립 검토, 별도 Claude 독립 감사.
- 최초 목표·완료 기준·허용 경로 고정. AI가 변경할 수 없다.
- 다음 지시는 최대 2개.
- 구현 주기 시작 후 1시간 또는 현재 지시 완료 중 먼저 오는 시점에 검토 절차 개시.
- 검토 중 구현 프로세스는 정지하고 고정된 스냅샷을 사용한다.
- 연속 3회 무진전 또는 전체 경과 시간 4시간에 중단한다.
- 최신 코드에 대한 필수 검사·검토·감사 통과 후 로컬 보고한다.

## 2. 상태 전이

| 상태 | 정상 전이 | 실패 처리 |
| --- | --- | --- |
| PREPARING | 계약·권한·기준 스냅샷 확인 후 IMPLEMENTING | 준비 실패로 중단 |
| IMPLEMENTING | 완료 또는 주기 만료 시 QUIESCING | 안전 위반은 즉시 중단 |
| QUIESCING | 모든 소유 자식 프로세스 종료 확인 후 SNAPSHOTTING | 종료 확인 실패 시 중단 |
| SNAPSHOTTING | 고정 사본 생성 후 CHECKING | 비밀정보·허용 경로 위반 시 중단 |
| CHECKING | 성공·실패 증거를 저장하고 REVIEWING | 검사 시간 초과도 실패 증거로 기록 |
| REVIEWING | 유효한 결과 수신 후 AUDITING | 한정 재확인 후 중단 |
| AUDITING | 유효한 결과 수신 후 DECIDING | 한정 재확인 후 중단 |
| DECIDING | IMPLEMENTING, COMPLETED 또는 STOPPED | 불명확하면 중단 |

어느 상태에서든 취소·전체 시간 만료·정책 위반은 종료 절차로 진입한다. 종료 시 새 검사나 AI 호출을 시작하지 않는다. 상태와 보고서를 먼저 저장하고, 보고서 생성 실패는 별도 오류로 기록한다. COMPLETED와 STOPPED는 명시적 재개 승인 없이 실행을 시작하지 않는다.

검사 실패가 있어도 코드 검토와 감사에는 실제 실패 증거를 전달한다. 운영 실패로 증거 확보가 불가능하면 완료를 인정하지 않는다.

## 3. 시간과 프로세스 제어

전체 마감은 최초 시작 시각 + 14,400초다. 재개해도 같은 실행의 마감은 초기화하지 않는다. 따라서 중단·컴퓨터 종료 중의 시간도 포함한다. 이는 '전체 경과 시간'을 문자 그대로 적용한 제안이다. 만료 후 계속하려면 사용자 승인으로 새 실행을 만들고 이전 이력을 연결한다.

프로세스가 살아 있는 동안은 단조 시계를 사용하고, 재시작 시 저장된 UTC 마감을 함께 검증한다. 시스템 시계 역행이나 모순을 감지하면 자동 연장하지 않고 중단한다.

1시간은 Codex 구현 구간의 최대 길이다. 검토·감사 이후 새 구현 구간의 타이머를 시작하되 전체 마감은 유지한다. 각 작업 제한 시간은 자체 한도와 전체 잔여 시간 중 작은 값이다.

CLI가 협조적 정리 요청을 지원한다고 가정하지 않는다. 지원 여부를 어댑터가 확인하고, 미지원이면 종료 신호와 유예 후 소유 프로세스 트리를 종료한다. 같은 이름의 다른 CLI 프로세스는 종료하지 않는다. 모든 자식 종료를 확인하지 못하면 스냅샷을 검토하거나 완료 처리하지 않는다. 구체적인 Mac·Windows 종료 방법은 실제 어댑터 구현 시 검증한다.

## 4. 데이터 계약

모든 레코드는 schema_version, run_id, cycle_id(해당 시), 생성 시각을 가진다. AI는 아래 필드 중 자신의 결과 부분만 제안한다. 식별자·실제 시각·해시는 관리자가 생성하거나 검증한다. JSON Schema로 필수 필드, 열거값, 최대 길이와 추가 필드 금지를 검사한다.

| 레코드 | 주요 필드 |
| --- | --- |
| 작업 계약 | goal, criteria[{id, description, evidence_rule}], allowed_paths, forbidden_paths, checks[{id, argv, timeout}], limits, publish=never, contract_hash |
| 지시 | instruction_id, criterion_ids, finding_ids, action, expected_evidence; 목록 길이 1~2 |
| 스냅샷 | snapshot_id, contract_hash, baseline_id, manifest[{path, sha256}], diff_digest |
| 검사 | check_id, snapshot_id, argv, exit_code, status, duration, evidence_id |
| 검토 | snapshot_id, verdict, findings[{id, severity, criterion_id, location, evidence_ids, explanation}], next_candidates |
| 감사 | snapshot_id, review_id, goal_alignment, evidence_integrity, progress_claims, risks, recommendation |
| 판정 | snapshot_id, decision, reason_codes, accepted_progress_ids, no_progress_count, next_instructions |

검토 verdict는 pass / changes_requested / inconclusive다. 감사 recommendation은 continue / complete / stop이며 최종 판정 권한은 없다. 필수 증거가 없으면 inconclusive로 처리한다. 경로·증거 참조·계약 연결이 유효하지 않은 지적은 자동 승인 근거로 사용하지 않는다.

스냅샷 manifest에는 허용된 입력 파일 전체를 포함하고 비밀정보는 AI 전송 전에 차단한다. 링크를 통한 경로 이탈, 대소문자·정규화 차이도 검사한다. 검사 전후 해시가 달라지면 그 검사 결과를 원래 스냅샷의 근거로 쓰지 않는다. 변경이 필요한 검사는 별도 임시 사본에서 수행한다.

## 5. 판정 순서

1. 취소·안전 위반·마감·호출 한도를 먼저 확인한다.
2. 계약 해시와 최신 코드가 검사·검토·감사의 대상과 같은지 확인한다.
3. 모든 완료 조건을 충족하면 COMPLETED로 판정한다.
4. 이전에 달성하지 않은 유효한 진척을 집계한다.
5. 진척이 있으면 연속 무진전 횟수를 0으로, 없으면 1 증가시킨다.
6. 3회에 도달하면 STOPPED로 판정한다.
7. 남은 목표에 연결된 실행 가능한 다음 지시를 최대 2개 선택한다. 지시가 없거나 충돌이 해결되지 않으면 중단한다.

최초 스냅샷을 기준선으로 저장한다. 완료 기준은 한 번 처음 충족한 경우에만 새 진척으로 인정한다. 실패 검사 최초 해결과 검증된 지적 최초 해소도 이력을 유지한다. 단순 파일 변경, 지적 이름 변경, 동일 결함의 재발·재해결은 새 진척이 아니다. AI가 제안한 의미적 중복 판정이 불명확하면 진척으로 인정하지 않는다. AI가 새로 만든 지적만 계속 해결하여 정체 카운터를 초기화하지 못하도록 최초 목표 연결과 실증 검사를 요구한다.

심각도 제안: critical(안전·데이터 손실), high(핵심 기능 실패), medium(일반 결함), low(개선). critical/high/medium 미해결은 완료를 막고 low는 보고서에 남긴다. 이는 미확정 정책이며 구현 전에 확정한다.

## 6. 독립 세션과 지시 전달

검토자는 계약·스냅샷·검사 증거를 받는다. 감사자는 여기에 주기별 지시·검토 결과·진척 이력을 추가로 받는다. 세션 재사용 없이 별도 호출한다. 이전 이력은 무제한 원문 대신 근거를 추적할 수 있는 구조화 기록으로 전달한다.

Python이 구조·참조·우선순위를 검증한 지시 후보만 Codex에 전달한다. Python 자체가 자연어 의미를 완벽히 판별한다고 가정하지 않는다. 목표 연결이 불명확하면 재확인하거나 중단한다. 검사 명령은 승인된 계약에서만 가져오며 AI 결과의 명령을 그대로 실행하지 않는다.

## 7. 저장과 재개

실행 데이터는 도구·작업 저장소 밖에 둔다. 상태 변경과 이벤트 저장은 원자적으로 처리하고, 같은 실행을 두 관리자가 조작하지 못하도록 잠근다. 중단 도중 재시작되면 기존 프로세스 존재와 소유권을 먼저 확인한다. 불명확하면 중복 실행하지 않는다.

재개 조건: 사용자 요청, 동일 계약, 마감 미도달, 중단 원인 해소, 프로세스 정리 완료. 파일이 바뀌었으면 승인 상태를 폐기하고 새 스냅샷부터 검사한다. 목표 변경·마감 만료는 연결된 새 실행으로 처리한다. 안전 중단의 원인이 해결되지 않으면 사용자 요청이 있어도 실행 준비 실패로 보고한다.

## 8. 제안 기본값 — 추가 확정 필요

| 항목 | 제안 |
| --- | --- |
| 작업 종료 유예 | 최대 60초, 이후 소유 프로세스 강제 종료 |
| Claude 검토 / 감사 | 각각 호출당 10분 |
| 필수 검사 | 명령당 기본 10분, 계약에서 명시적으로 변경 |
| 통신 오류 재시도 | 최대 2회, 10초·30초 간격; 마감과 호출 한도 포함 |
| 잘못된 결과 형식 | 1회 재확인, 실패 시 중단 |
| 전체 AI 프로세스 호출 | 재시도 포함 30회 |
| 비용 | 실제 금액을 관측할 수 없으면 금액 상한 보장 표기 금지; 시간·호출 수 제한 제공 |
| 기록 | 기본 구조화 요약, 원본 stdout/stderr 영구 저장 꺼짐 |

원본 로그 저장을 끄더라도 CLI 자체의 세션 기록·제공자 보관이 없어지는 것은 아니다. 실제 인증·기록·샌드박스 제어는 연결 전에 공식 문서와 설치 버전으로 확인한다.

## 9. 첫 구현의 검증 시나리오

실제 AI와 키 없이 가짜 CLI·가짜 시계·임시 작업 폴더로 검사한다.

- 조기 작업 완료 및 1시간 경계에서 단 한 번 검토 시작.
- 필수 검사 실패를 완료로 오인하지 않고 감사 후 다음 지시 최대 2개 생성.
- 세 번 연속 무진전 시 종료, 진척 발생 시 카운터 초기화.
- 같은 결함의 재발·해결과 이름 변경은 새 진척으로 인정하지 않음.
- 최신 파일 변경으로 이전 승인 무효화.
- 검토 도중 4시간 만료 시 자식 종료·상태 보존·새 호출 차단.
- 인증 오류, 잘못된 JSON, 누락 증거, 충돌 결과를 통과 처리하지 않음.
- 취소·강제 종료·관리자 재시작·동시 실행 잠금·마감 유지 확인.
- 금지 경로·심볼릭 링크 이탈·비밀정보·계약 변경 차단.
- macOS·Windows에서 한글 경로 및 자식 프로세스 정리 확인.

## 10. 다음 구현 범위

첫 코드 변경은 데이터 모델, 결정 함수, 가짜 시계·CLI와 로컬 보고서까지로 제한한다. 실제 Codex·Claude 연결, 스킬 설치, GitHub 자동 게시는 후속 단계다. 문서 검토 후 제안 기본값을 확정하고 이 시나리오를 테스트로 구현한다.
