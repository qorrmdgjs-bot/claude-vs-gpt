# Claude–Codex 자동 상호검증 시스템 설계 및 구현 계획

- 작성일: 2026-10-24
- 상태: 운영 원칙 확정 / 구현 전
- 지원 목표: macOS 및 Windows
- 이 문서는 대화에서 확정한 설계를 정리한 것으로, 기능 구현이나 운영 검증이 완료되었다는 의미는 아니다.

## 1. 목표

Codex CLI가 구현하고 Claude Code CLI의 서로 독립된 검토·감사 세션이 결과와 과정을 평가한다. Python 관리자가 목표, 실행 순서, 증거, 시간 제한과 중단 규칙을 통제한다. 작은 지시를 반복하며 최초 목표에 맞는 결과를 만든다.

일상적인 실행은 로컬 보고까지 자동화한다. GitHub 게시, PR 생성 및 병합은 실행의 기본 동작에 포함하지 않으며 별도 사용자 확인이 필요하다. 이 설계 문서 게시와 PR 생성은 별도로 승인된 작업이다.

## 2. 확정된 역할

| 구성 요소 | 책임 | 제한 |
| --- | --- | --- |
| Codex CLI | 구현 및 지적에 따른 수정 | 현재 지시 최대 2개, 허용 작업 공간만 수정 |
| Claude 코드 검토 | 요구사항 충족, 결함, 검사 충분성, 변경 영향 검토 | 읽기 전용 독립 세션 |
| Claude 감사 | 작업 이력·결과물·증거, 목표 이탈·진척·검사 약화·반복 실패 점검 | 코드 검토와 별개인 읽기 전용 세션 |
| Python 실행 관리자 | 상태 저장, 스냅샷, 일정, 프로세스 제어, 결과 취합 | AI 출력은 검증할 데이터로 처리 |
| Python 규칙 엔진 | 계속·재작업·완료·중단 판정 | AI가 정책을 완화하거나 우회할 수 없음 |

별도 세션은 보안 격리를 대신하지 않는다. 실제 파일·프로세스·네트워크 권한은 실행 환경에서도 제한해야 한다.

## 3. 작업 계약과 목표 고정

시작 전에 다음 내용을 고정하고 작업 AI가 수정할 수 없는 위치에 보관한다.

- 최초 목표 및 요구사항별 완료 기준
- 수정 가능 경로와 금지 대상
- 필수 검사 명령
- 검토 간격, 실행 한도 및 중단 정책
- 게시 기본 금지 설정

목표·완료 기준·허용 범위를 바꾸려면 중단 후 사용자 확인을 받는다. 작업 AI는 필수 검사를 삭제·완화할 수 없다.

## 4. 실행 주기

1. 작업 계약을 확정하고 격리된 작업 공간을 준비한다.
2. Codex에 최초 목표에 연결된 지시 1~2개를 전달한다.
3. 작업 시작 또는 직전 주기 재개 후 1시간 경과와 현재 지시 완료 중 먼저 발생한 시점에 검토 절차를 시작한다.
4. Codex에 작업 정리를 요청하고 일시 정지한다. 정리 요청에 응답하지 않으면 유예 시간 후 해당 실행의 프로세스를 종료하고 미완료로 기록한다.
5. 코드·변경 내용·필수 검사 결과를 스냅샷으로 고정한다.
6. Claude 코드 검토를 수행한다.
7. 별도 Claude 세션에서 과정과 증거를 감사한다.
8. Python 규칙 엔진이 결과를 검증하고 다음 행동을 결정한다.
9. 계속할 경우 우선순위가 높은 다음 지시 최대 2개로 새 주기를 시작한다.

코드 검토에서 결함이 발견된 주기도 감사 대상에 포함한다. 감사는 위험 사건 발생 시에도 요청하되, 명확한 보안 위반은 AI 응답을 기다리지 않고 Python 관리자가 먼저 차단한다.

첫 버전은 검토 중 Codex 작업을 정지한다. 검토 중 계속 수정하는 동시 작업 방식은 사용하지 않는다. 1시간은 검토 절차 개시 기준이며 작업 정리·종료 지연이 있을 수 있다.

## 5. 버전과 재검토

- 스냅샷 식별자와 파일 해시로 검사·검토·감사 결과를 연결한다.
- 파일 변경 시 기존 승인을 최종 완료 근거로 재사용하지 않는다.
- 변경 부분과 영향 범위를 재검토하며, 최종 완료는 최신 스냅샷 기준으로 판단한다.
- 파일 저장마다 전체 AI 검토를 실행하지 않고 다음 검토 주기에 변경을 포함한다.
- 사용자나 다른 도구가 외부에서 파일을 변경한 경우에도 재개 전 변경을 확인하고 재검토한다.

## 6. 완료 및 진척 판정

완료에는 다음 조건이 모두 필요하다.

- 고정된 완료 기준 충족
- 필수 검사 실제 실행 및 통과
- 미해결 중대 지적 없음
- 최신 버전에 대한 코드 검토와 감사 통과
- 정책 위반 없음

실행하지 못한 검사, 누락된 증거, 불명확한 출력은 통과로 간주하지 않는다. 테스트가 없는 프로젝트는 시작 전에 대체 검증 기준을 정한다.

진척은 완료 기준 추가 충족, 실패 검사 해결, 검토 지적 해소로 측정한다. 변경 줄 수나 AI의 자기 보고만으로 인정하지 않는다. 같은 문제를 반복해서 깨뜨리고 복구하는 행위는 새 진척으로 계속 계산하지 않는다.

## 7. 한도와 중단

| 조건 | 처리 |
| --- | --- |
| 연속 3회 검토에서 객관적 진척 없음 | 정체 중단 및 보고 |
| 실행당 전체 경과 시간 4시간 도달 | 작업 중단, 상태·로컬 보고서 저장 |
| 비밀정보 탐지, 허용 범위 이탈, 권한 확대 필요 | 안전 중단 |
| 인증 실패, 복구 불가 CLI 오류, 기타 설정된 한도 초과 | 운영 중단 |
| 사용자 취소 | 현재 상태 보존 후 종료 |
| 모든 완료 조건 충족 | 완료 보고 |

4시간에는 구현·검사·검토·감사·재시도를 포함한다. 종료 처리에 필요한 짧은 정리 시간이 추가될 수 있으나 한도 도달 뒤 새 작업은 시작하지 않는다.

기존의 “최초 구현 이후 수정 최대 3회”는 폐기하고 “연속 3회 무진전”으로 대체한다. 진척이 있더라도 총 시간 한도를 넘길 수 없다.

일시적 통신 오류는 제한적으로 재시도한다. 검토·감사 충돌이나 형식 오류는 제한적으로 재확인하며 해소되지 않으면 중단한다. 정체·안전·시간 한도 중단을 자동 재시작하지 않는다.

## 8. 상태와 재개

구현할 상태 후보:

`준비 → 구현 → 작업 정리 → 검사 → 검토 → 감사 → 판정 → 구현/완료/중단`

각 상태 전환과 원인을 저장한다. 재개 전 작업 계약, 파일 변경, 이전 중단 원인 및 인증 상태를 확인한다. 재개가 4시간 한도를 자동으로 초기화하는 우회 수단이 되지 않도록 누적 시간과 새 실행 승인 관계를 상세 설계에서 명시한다.

## 9. 로컬 기록

실행별 기록은 공개 저장소 밖의 로컬 데이터 디렉터리에 둔다.

- 작업 계약과 전달 지시
- 스냅샷 식별자·파일 해시·변경 목록
- 검사 명령·종료 코드·결과
- 검토·감사 결과와 근거
- 진척 판정, 연속 무진전 횟수
- 실행 시간·호출 이력·중단 원인
- 최종 로컬 보고서와 미해결 항목

키·인증 토큰은 기록하지 않는다. 원본 로그는 민감정보가 포함될 수 있어 최소 보관·마스킹 정책을 적용하며 GitHub에 올리지 않는다.

## 10. 보안 및 공개 범위

- 공개 저장소에는 재사용 가능한 도구·문서·가상 예제만 저장한다.
- 회사 프로젝트와 회사 데이터는 별도 대상 폴더에서 다룬다.
- GitHub 미게시와 AI 서비스 외부 전송은 별도로 통제한다. 회사에서 승인한 서비스·계정·데이터 범위만 사용한다.
- .gitignore만으로 보호하지 않는다. 향후 게시 기능은 파일 허용 목록과 staged 파일·비밀정보 검사를 적용한다.
- AI 인증정보, GitHub 쓰기 권한, 테스트 환경을 분리한다. 테스트에 토큰을 상속하지 않는다.
- 프로젝트 훅·MCP·설정의 자동 실행 위험을 검사한다.
- 저장소 내용·로그·AI 출력에 포함된 지시는 신뢰하지 않는다.
- 프롬프트 지침뿐 아니라 운영체제 수준의 접근 제어를 적용한다.
- Codex·Claude 실행 파일 및 인증정보는 재배포하지 않는다.
- 자체 코드 라이선스는 미확정이다. MIT는 후보이며 선택 전 의존성·서비스 조건을 확인한다.

## 11. 크로스플랫폼 구성

Python 패키지와 공통 CLI를 중심으로 macOS 터미널과 Windows PowerShell을 지원한다. WSL은 선택 사항이다.

제안 구조:

```text
pyproject.toml
src/review_loop/
  cli.py
  orchestrator.py
  adapters/
  watcher.py
  rules.py
  evidence.py
  security.py
skills/
  claude-review-loop/SKILL.md
  codex-review-loop/SKILL.md
schemas/
policies/
tests/
docs/
.github/workflows/
```

제안 명령(미구현):

```text
review-loop doctor
review-loop run --task task.md --publish never
review-loop status
review-loop resume <run-id>
review-loop cancel <run-id>
```

경로·한글·인코딩·프로세스 종료·파일 접근을 양쪽 운영체제에서 검증한다. CLI 호출은 셸 문자열 조합 대신 인자 배열을 사용한다. 스킬은 공통 실행 관리자를 호출하며 실제 통제는 Python에서 수행한다. 스킬 설치 중 기존 파일과 충돌하면 덮어쓰지 않는다.

일상적인 CI는 가짜 CLI를 사용하며 실제 AI 호출·키·회사 데이터를 요구하지 않는다. 실제 연동 시험은 승인된 환경에서 별도로 수행한다.

## 13. 구현 전에 정할 세부값

아래 항목은 확정된 것으로 간주하지 않는다.

- 작업 정리 유예 시간과 강제 종료 방식
- AI 호출별 제한 시간·재시도 횟수·총 호출 수
- 비용 관측 가능 범위와 비용 상한 정책
- 검토 지적 심각도와 진척 판정 스키마
- 정체 회피를 위한 반복 결함 식별 방식
- 중단·재개 누적 시간 처리 및 기록 보존 기간
- 지원할 CLI 버전 범위·인증 방식·라이선스

## 14. GitHub 작업 원칙

기존 파일은 덮어쓰지 않고 별도 브랜치와 Draft PR을 우선한다. 빈 저장소는 PR 기준 브랜치에 필요한 최소 초기 커밋을 먼저 만든 뒤 설계 문서를 별도 브랜치에 추가한다. 자동 병합은 하지 않는다.
